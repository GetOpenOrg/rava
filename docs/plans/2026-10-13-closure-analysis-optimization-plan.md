## 一、核心裁决（三方一致 + 内部证据支持）

**不删除闭包分析，改造为"有界、分层、可降级"的分析。** 删除（= 全 classpath 翻译）的硬代价：
最小档案约束失效、rustc 时间与体积按 classpath 线性爆炸、虚分派全保守化、逃逸分析仍不可省（无 GC
模型必需）；反射重的六库里有运行时字节码生成路径（javassist `toClass` / CGLIB / ASM 后端），在
"无动态类加载"前提下**原则不可翻译**——这是闭包之外的独立裁决点，与去不去分析无关。

**主矛盾重判（专家 2 论点，内部证据支持）**：合法不动点状态只有 1–2.5G 而 RSS 单调无平台，
更像**不收敛（bug/无界实体）而非状态太大（容量）**——先诊断再优化，"修 bug"与"降容量"路径完全不同。

## 二、解法清单（S1–S14，按落地顺序分组）

### 阶段 0：诊断（先做，决定后面走哪条路）

- **S1 迭代内真实水位埋点**（三方一致首位；内部"记账脱钩"四条共性之一）
  每轮记录：上下文总数、各集合基数总和、worklist 入队/重入计数、新增事实数；配计数分配器
  （计数 allocator / dhat）把"真实存活"与"分配器碎片/临时集合"分开；RSS 与自报对齐后才能做
  "超预算降级"。判据：**"重入但新增为 0" = bug；新增持续非 0 = 格无界**；集合基数总和曲线有拐点
  = 慢收敛，持续线性/加速 = 不收敛。
- **S2 无限实体链排查**（专家 2 最可疑根因假设）
  六库共性是运行时生成字节码/代理。排查分析器是否在给 `ClassPool.toClass` / `defineClass` /
  `Proxy.newProxyInstance` 建模时**按上下文 × 调用点动态合成新类型/上下文**（实体名混入迭代号/
  计数器即实锤）——这直接形成无限上升链。处置：生成类按生成点命名（有限化）、字符串反射域 widening
  （退化为"任意"）。

### 阶段 1：止血（短期逃生阀，与主算法并行，不动语义）

- **S3 污染源注册表模式**（专家 3 短期补丁 + 专家 1/2 的 JVM-oracle 优势）
  本项目独有优势：**golden 跑批本来就要跑 JVM 对账**——挂 tracing agent 采集实际发生的反射/
  代理/序列化类，生成显式注册表当种子（native-image tracing agent 同模式，零额外成本）；
  jackson 等社区已有 reachability-metadata 可参考。检测进入污染路径（javassist/jackson/
  fastjson2…）即切换注册表保守模式，截断 worklist 无界推导。注意：注册表覆盖只到被测路径，
  等价性契约需写明"注册表即档案成员"。
- **S4 收敛判定改写：epoch worklist + 差分传播**（专家 1/3 同款；治浪费源④）
  **删掉全局 `is_subset` 不动点判定**——收敛 = 本轮无增量 diff；worklist 条目带版本号，取出时
  节点版本 ≥ 条目版本即跳过；入队仅基于集合真实增长（changed）。hub 边集改**延迟物化**（dirty
  标记，节点被取出才合并增量），插入前 `new \ existing` 只追加差集；区分 provenance 边与临时
  推导边，后者不落主存。

### 阶段 2：表示层改造（内存大头）

- **S5 集合表示：稠密整数 ID + 分层集合**（三方一致；治浪费源②）
  类型/方法/分配点全部整数 ID；小集合有序小数组（≤16）→ 中等 hashset → 大集位图（roaring/
  hybrid）→ **超大集 TOP 保守标记**（不再枚举，见 S6 饱和）。`is_subset`/union/intersect 变
  按字运算。BTreeSet 是当前最差选择（节点分散、逐元素比较、churn 产生碎片）。**先换分配器
  （mimalloc/jemalloc）复测一次**，把碎片从数据里分离。
- **S6 饱和机制（saturation）**（专家 1/2 重点推荐，Graal native-image 实装，
  PLDI 2024 *Scaling Type-Based Points-to Analysis with Saturation*）
  类型流超过阈值（Graal 默认 ~20）即标记饱和：不再精确传播，消费者订阅"声明类型的全部已实例化
  子类型"共享节点；饱和是单向终态，**天然保证终止**。同时治②③④。**等价性关键**：饱和是可靠
  （sound）过近似——退化成完整 vtable/itable 分派，不漏；`dyn miss 0` 要求的是不漏不是精确，
  精确度只影响体积与去虚化率。降级点在日志显式标记，保持可审计。
- **S7 上下文模型重构**（治浪费源①，单源 ~16G：402K × 40KiB）
  默认**上下文不敏感**（native-image 默认形态）；选择性开启（Doop 系经验：Introspective /
  Zipper / Scaler——先跑不敏感遍，按指向集大小挑"会爆"的方法关闭上下文）；**硬上限 + 超限折叠
  回无上下文副本（widening）**；上下文与方法体状态分离、持久化共享（写时复制 + dirty 标记），
  禁止整对象克隆；**污染源标记**（`Class.forName`/代理/序列化入口）强制降敏感度。
- **S8 hub 边集压缩**（治浪费源③；与 S4 延迟物化叠加）
  键 interned ID；SCC 折叠（hub 图上离线 + 在线检测，同环节点共享集合）；52 MiB/s 的持续
  insert 大概率是全量追加无差集 + 重复元素，S4 的差分插入直接消掉大半。

### 阶段 3：架构层（终态形态）

- **S9 分层降级架构**（专家 1 四层 / 专家 2 两级的合流）
  L0 地板层：**RTA/CHA 闭包**（类层次 + 已实例化类型；近线性、单调、必然收敛、内存小）——
  给出保守可靠的可达集与分派上界，**所有降级的统一落点**；L1 精化层：0-CFA 类型流 + 饱和 +
  差分 + 位集（预算内运行）；L2 选择性上下文层（少数方法 + 上限）；预算触发（上下文数/基数总和/
  迭代轮数/RSS 任一越线）自动退回上层保守结果并打标，**而不是继续长**。
- **S10 逃逸/物化与全局不动点解耦**（专家 1/2 独立结构建议）
  native-image 的 PEA 在闭包之后逐方法编译时做，不在全局 worklist 里。我们的物化决策若与可达性
  同迭代，会把全局状态放大——改为闭包只管可达与分派，物化逐方法后置分析（用闭包结果做摘要），
  饱和值一律按逃逸处理。
- **S11 "正确且最小"约束改写**（专家 2 提出，本线细化；涉及 CLAUDE.md 不变量 #2 及多处计划文档表述）
  - **问题**：开放世界（反射 / 动态代理 / 运行时生成字节码）下，真实运行期可达集**不可精确静态判定**，
    "最小"若隐式绑定"最精确分析"，则 S6 饱和 / S9 分层降级产生的**声明式保守过近似**（多包含类型）
    会被误读为违反"最小"，堵死降级路线；
  - **改写为三条可判定的含义**：① **档案 = 声明分析级别的输出**——分析级别是构建的显式参数
    （如 `closure-level: rta | 0cfa | 0cfa-saturated`），写入档案元数据并纳入内容摘要/缓存键
    （级别变化 = 摘要变化，与 D6"拆分确定、机器无关"原则对齐）；② **不漏**（sound：该级别
    应含的类与方法全在档案内）；③ **不塞**（禁止为编译通过手工加类——原禁止条款**原样保留**）；
  - **等价性不受影响**：golden 对账要求的是行为等价（不漏即满足）；保守多余类型只影响体积与
    去虚化率，按 §四护栏的"漏类型 = bug / 多类型 = 安全"二分解读；
  - **已裁决并改写（2026-10-13）**：CLAUDE.md 第 2 条已落三条含义（档案=级别输出 / 不漏 /
    无人工增量；`closure-level` 显式参数入元数据与摘要）；V12 / crate-split 等计划文档的
    "正确且最小"字样引用处在各线触及时随改。
- **S12 切片缓存（既有立项对齐）**：V12 按库切片 + 内容键缓存——"一次分析全局复用"，与上述
  全部兼容，属放大器不属于解法本身。

## 四、等价性护栏（golden 对账相关）

- 饱和/降级是 **sound 过近似**：多包含类型 = 安全（分派表变大），漏类型 = bug（必须修）；
  golden 与 `dyn miss` 指标要按此二分解读，**不为点亮反向压缩保守集**；
- 降级点显式打标（"本调用点因饱和降级"），保持可审计；
- 验收对账基线：T6 权威清单 + junit 族三档带 + 六库病理卡，每落一步重扫画水位线（已登记节奏）。

## 五、地板与水位预期（校准口径）

- 内部推算 2–4G（状态本体 1–2.5G 实测）；专家 1/2 认为该值**偏保守**——1–2.5G 本身是
  BTreeSet + 40KiB 上下文表示下量出的，换 ID+位集+不敏感+饱和后可能 **1G 内甚至几百 MB**；
- 校准公式：`Σ(流节点数 × 平均集合大小 / 8 字节)` + 每方法流图固定开销，先估再测；
- 同类水位参照（专家印象值，勿当基准）：native-image 常规 2–5G / 重反射 4–8G（带降级）、
  无上限上下文 15–30G+；R8 1–3G；Doop 深上下文 20–80G（与我们症状一致——佐证问题在
  上下文策略与收敛，不在问题本体）。
- **>12G 即视为失控，不是理论必需**——与"32G 有 4–8 倍余量后收紧 16G"的阶梯自洽。

## 九、S4 实施记录（2026-10-14，`g1-ctx2` 2826315f/78da04f4/00598f20，未合入）

**S4 设计对位（方案原文 → 本库现状）**：方案三件套中，①「删全局 is_subset 不动点判定 /
收敛 = 本轮无增量 diff / 入队仅基于真实增长 / worklist 版本号」在本库**已在位**（§4.5/§4.6：
`add_to_id` 差分并入、`graph.delta` 按节点累积 + `queued` 去重 + 批量排空——epoch worklist
语义等价物，无全局判定可删）；②「hub 边集延迟物化（dirty 标记，节点被取出才合并增量）」与
③「区分 provenance 边与临时推导边，后者不落主存」**本轮实施**——hub 路由边（HP→P 形参向 /
R→HR 返回向）由 (h→t) plain 路由关系可重导出，即临时推导边。画像（census edges 边种类矩阵，
新增观测）：语料深例路由边占全边 40%+，sb3 死点图边 1360 MiB + seen 索引 55.0M 槽为死点
第一大块。

**首版（78da04f4，撤回）**：双向惰性 + 有序集扇出 + plain_rev 逆表。集合与 mc 逐位相同但
**DeepCopy 三种子折叠口径 DIFF**（folds 死代码 / 常量折叠统计跨种子置换）——根因是**推送
次序漂移**：R(t) 出边表里路由边与站点结果边按接入交错，惰性扇出把路由推送移到排空末尾必改
序；折叠事实依赖分析时点（catch/instanceby 目标类型按当下 G 判活）。**教训：不动点集合序
不敏感、折叠口径序敏感——改推送序的改造必须逐位复刻原序或全量重验折叠**。

**终态 PATH B（00598f20）**：只惰性化 HP→P 向——HP 节点出边表本就只有路由边（无交错），
`plain_seq`（插入序镜像，8 B/中转目标）使扇出序与边表序逐位一致：接入时 `push_now`（flow

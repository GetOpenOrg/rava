**方法粒度**（实现层 23,008 个「文件 + fn 名」键）：
- 总是存根：11,487；
- 有的测试存根、有的测试翻译：2,416；
- 总是翻译：9,105。
- 在 ≥2 测试中都被翻译的 8,619 个 fn 里，翻译文本全同的占 95.8%（按字节 94.1%），签名不同的只有 77 个。

结论：**一个方法一旦翻译，它的文本基本与测试无关。** 生成结果随测试变化，来自以下五个闭包相关的决定：
1. 方法集合：存根还是体，以及 vtable 槽保留哪些。这是主因，按类看去掉方法后一致率从 47% 升到 87–91%。
2. 签名中闭包外的类型降级为 `Object`。例如 `String.transform(f: Object)` 与 `(f: Function<Object, Object>)`。
3. `use` 列表与名字消歧别名，例如 `Era` 与 `sun_util_calendar_Era`。它们取决于闭包里同时有哪些类。
4. 依赖全程序事实的折叠：
   - `fold_null_recv`：没有实例化实现时，接收者必为 null；
   - 实例化集合决定的直接返回，例如 `Long.toString` 的退化形；
   - Digester 有 null_recv 折叠 125 处，常量折叠 794 处。
5. 静态字段与类级属性按使用裁剪：`rava_moved` 标记、`superclass_fields`、`cfg_attr`。

  - 常量折叠与 noreturn 在档案的多根分析上计算。只依赖 JDK 内部事实的部分不受开放世界影响；由 null_recv 派生的 noreturn 随 null_recv 一并按开放世界处理（已计入上面的一阶增量）。

## 二、终态路线比较

### 路线 (b)：按内容寻址的 crate / 产物缓存

- 做法：以「crate 源码哈希 + 依赖 crate 哈希 + 工具链 + 编译参数」为键缓存 rlib / rmeta，命中即跳过编译。8 台服务器共享一个缓存。
- 上限：受 1.3 的五类闭包相关决定约束，同一个 JDK 类在不同测试中多数不同版本，声明层 crate 更是整体不同。
  - 实测 crate 粒度命中约 17%。
  - 拆细粒度也不行：JDK 类型成环（§三，见 `2026-10-01-rustc-memory-and-crate-split.md`），声明层不能拆到类粒度。
  - 整体机时只降约 0.17 × 25 ≈ 4 机时，到约 31 机时。
- 文本归一能提高单类一致率（去 `use` / 注释后约 43%），但不改变 crate 粒度的结论。
- 结论：单独做 (b) 收益小。它的价值是作为 (a) 的分发机制。

### 路线 (a)：类的翻译与测试无关，可达性只在链接层决定

**核心**：JDK 部分的生成结果只取决于 (JDK 版本, 生成器版本, 手写 runtime 版本, **JDK 档案**)，与具体测试无关。
- 「JDK 档案」(profile) 是一份确定的类 / 方法集合：语料全体调用链的并集，加上种子。
- 档案对应的 `java_runtime` 与 `java_body_*` 只编译一次，所有测试共享。
- 每个测试只转译、编译用户 crate 并链接。

**1.3 中五类差异各自的终态处理**：
1. 方法集合：存根还是体按档案定，不按单个测试定。档案内的方法全部翻译；档案外的方法生成存根。
2. 签名降级：只对档案外的类型降级，与测试无关。
3. `use` 与消歧别名：只取决于档案内类集合，与测试无关。
4. 全程序折叠：分两类处理。
   - 只依赖 JDK 内部事实的折叠：常量、系统属性、noreturn。它们在档案上计算，照常保留。
   - 依赖「实例化集合」的折叠（`fold_null_recv` 一类）：对用户代码可扩展的类型（非 final、非 sealed 的公开类与接口）必须按开放世界处理，即不做「无实现 → null」折叠。理由是用户类可以实现 JDK 接口，而档案不能依赖用户类。对 final 类、私有和静态目标照常做。
   - 精度代价（§1.7 实测）：全集 448 个 null_recv 折叠点中，开放世界额外放弃 144 处；闭包一阶增量 +113 个方法（+0.55%）、+0 个类。
5. 静态字段 / 类级属性的裁剪按档案定。

**规模与编译代价**（§1.6 实测与外推）：
- 全集档案 3609 个类。声明层峰值现形态约 6.0 GB；做完 §7.5.4 第 1–7 项约 4.3 GB；再做 S7 约 3.0 GB。
- 实现层切为约 11 个 crate，每个 ≤ 1.3 GB。
- 档案构建每个键只做一次，现形态约 5 min 墙钟、约 0.12 机时。
- 单例：
  - JDK 部分零转译、零编译；
  - 只编用户 crate 加链接，rustc 实测约 1 s，终态目标见 §5.2；
  - 单例峰值由用户 crate 与链接决定，≤ 1 GB。
- 全量机时：从约 35 机时降到约 11 机时，编译部分从约 25 机时降到 ≤ 1.1 机时，细目见 §5.2。
- 二进制体积：全集档案静态链接的 debug 二进制约 350 MB。语料模式改为动态链接档案，单例二进制只含用户 crate，见 §4.4。

### 路线比较与 S7 的关系

| | (b) 内容寻址缓存 | (a) 档案化 | S7 统一对象句柄 + 描述符 |
|---|---|---|---|
| 解决什么 | 重复编译相同内容 | 消除内容随测试变化 | 单个 crate 的体量与 std 按类单态化 |
| 全量机时 | −4 机时 | −24 机时 | 单独做约 −30% 编译时间（体量 −58%） |
| 单例耗时 | 命中才降 | JDK 部分归零 | 声明层约 −55% |
| 互相关系 | (a) 的分发层：档案产物按内容寻址存取 | 档案声明层峰值现形态约 6.0 GB；§7.5.4 后约 4.3 GB，S7 后约 3.0 GB | 与 (a) **互补**：类代码只读描述符后，类级文本更少依赖闭包（1.3 的第 3、5 类差异进入描述符数据），档案切换时重编更少 |

- 三者**不冲突**：(a) 决定翻译什么，S7 决定每个类翻译成什么形态，(b) 决定产物怎么在机器间复用。
- 被 (a) 取代或降级的手段：
  - S4 / S5 拆层原本的目标之一「仅用户类变化时 JDK 零重编」由档案直接达成。拆层仍需要，因为档案的实现层体量大，必须分 crate 并行编译、控峰值。
  - §7.5.4 各项与 V1 仍然需要，它们决定档案声明层能否在单机内存内编完。
  - 逐例的 JDK 闭包精度优化（只为缩小单例 JDK 体量的那部分）在 (a) 下价值下降：单例不再编译 JDK。闭包分析器的精度改为服务档案总规模。

**统一推荐**：(a) 档案化 + S7 + (b) 作为档案产物的分发层。三者一起交用户一次决策。分发协议见第四节，实施顺序与量化目标见第五节。

## 三、与 CLAUDE.md 原则的协调（需要用户决策）

### 3.1 第 2 条改写：判定单位从单个程序改为档案

**今天的条文**：只分析调用链上的方法内部依赖；判定单位是单个程序（一个 `main`）。

**建议改写为**（只是方案，CLAUDE.md 由用户决定是否修改）：

> ### 2. 只分析档案调用链上的方法内部依赖
>
> 档案（profile）是一个构建单元全体入口的调用链并集，在开放世界下计算：
> - 生产构建：构建单元是一个用户项目，入口是该项目的全部 `main` 与种子；
> - 语料构建：构建单元是 e2e 全集，入口是全体测试的 `main` 与种子。
>
> ```
> 全体入口 → A() → B() → C()（native，手写）
> D()  ← 不在任何入口的调用链上，panic!("stub: ...") 存根，其依赖的类不被分析
> ```

> - 档案内的 JDK 类只翻译一次，生成结果与具体程序无关；单个程序的二进制可以含有它自己不可达、但档案可达的已翻译方法。
> - 依赖「实例化集合」的折叠（null 接收者等）只对用户无法扩展的类型做（final / sealed / 非公开 / 私有与静态目标）。
> - **禁止以「保证编译通过」为由**把不在档案调用链上的类加入生成范围。

**不变的部分**
- 存根机制与 `panic!` 消息格式；
- 「不分析存根依赖」；
- 「禁止为编译通过扩大范围」。

**代价**
1. 单例二进制含档案可达的方法。语料模式动态链接档案（§4.4），单例二进制只含用户 crate；生产构建的档案就是项目自身的闭包，体积与今天等价。
2. 档案外的新程序先扩展档案，触发一次档案重建（现形态约 5 min、0.12 机时，§1.6）。语料新增测试时，若该测试的 JDK 闭包已被档案覆盖，则不重建（§4.1）。
3. 开放世界折叠的精度代价：全集放弃 144 个 null_recv 折叠点，闭包增加 0.55% 的方法、0 个类（§1.7）。
4. 闭包分析器的「逐例最小」目标改为「档案最小」：
   - 衡量口径从单例 JDK 类数（中位 349）变为档案总规模（3609 类）；
   - 只缩小单例 JDK 体量的精度工作价值下降；
   - 缩小档案并集的工作价值不变。
5. CLAUDE.md 连带需要改的段落（只列出，不改）：
   - 「工作区结构」：`build/<test>/java_runtime/src` 不再含 JDK 生成类，增加档案缓存目录 `~/.cache/rava/archive/`；
   - 「常用命令」：增加档案构建命令；
   - 「闭包目标：正确且最小」（记忆）：口径改为档案。

### 3.3 开放世界折叠

  - 档案键只依赖 JDK 侧的事实。新增或修改用户类不改变档案，测试改动不触发档案重建（§4.1）。

  - 代价只有 144 个折叠点，以及 +0.55% 的方法、+0 个类。

## 四、分布式缓存共享（终态协议）

**约束**
- 8 台服务器：ubuntu、jp1、jp2、kr1、kr2、sg1、sg2、us1，都装有 JDK 21 与 JDK 25。
- 调度方是本机，运行 `distribute_tests.py` / `dist_job.py`，经 SSH（paramiko）连接各服务器。连接失败按退避重试，并可降级走本机 SOCKS5 代理。
- jp2 只能经代理访问，链路不稳。
- 各服务器 checkout 路径不同，每个作业 / 抽查一个目录。

**设计原则**
- 唯一必须在线的是调度方。它是作业发起者，本来就必须在线。
- 任何一台服务器离线、链路中断都只影响它自己：它退化为本机构建，与其他机器不互相等待。
- 键一致，所以本机构建与拉取得到同一身份的产物。

### 4.1 键（两级，均含 JDK 主版本）

**L1 档案键** `P = sha256(...)`，输入为：
- JDK 主版本，即 `21` / `25`；
- JDK 镜像摘要：`$JAVA_HOME/release` 的 `JAVA_VERSION` 加 `lib/modules` 的 sha256；
- `generator/` 的 git tree 哈希；
- `runtime/` 的 git tree 哈希，含三份 TOML 清单与 `java_support/`；
- 档案内容摘要：多根开放世界分析得到的 JDK 侧类 / 方法 / 层级 / 折叠集合，规范化排序后的 sha256。

档案内容摘要只依赖 JDK 侧的并集，不含用户类，所以：
- 测试源码改动、新增测试，只要其 JDK 闭包被现有档案覆盖（类、方法、层级都是子集），就不改变 `P`；
- 覆盖判定由闭包分析逐例给出：测试闭包不是档案的子集时，作业把它并入并集，档案键随之改变，触发一次重建。

**L2 产物键** `B = sha256(...)`，输入为：
- `S`：生成的档案 crate 源码树摘要（`java_runtime`、`java_body_*`、JDK 部分 `java_meta`，含 Cargo 清单）；
- `rustc -vV` 全文（含 commit-hash 与 host triple）；
- 目标三元组；
- 编译参数：profile、opt-level、debuginfo、crate-type、`--remap-path-prefix` 规则。

**为什么分两级**
- `P → S` 是确定性生成，`rava` 两次生成确定性闸门已覆盖，见 `scripts/seed_check.sh`。
- `S → B` 隔离工具链。
- 两台服务器工具链不一致时，`P`、`S` 相同而 `B` 不同，各自构建，不会误用不兼容的 rlib。调度方据此报告工具链漂移。

**逐例闭包缓存键**（档案并集的输入）`C = sha256(...)`，输入为：
- 闭包分析器版本（`generator/` tree 哈希）；
- `runtime/` 清单 tree 哈希；
- JDK 镜像摘要；
- 测试源码及其依赖类路径摘要。

闭包分析器不变时，全集 1.9 机时的逐例闭包可以跨作业复用。

### 4.2 存储布局

| 位置 | 内容 | 保留 |
|---|---|---|
| 调度方 `~/.cache/rava/store/archive/jdk<M>/<B>.tar.zst` + `<B>.manifest.json` | 档案产物包（记录存储） | 每个 JDK 主版本最近 8 个键 |
| 调度方 `~/.cache/rava/store/index/jdk<M>/<P>` | `P → S → B` 映射、构建机、耗时、峰值 | 同上 |
| 调度方 `~/.cache/rava/store/closure/jdk<M>/<C>.json.gz` | 逐例闭包 | 最近 2 个分析器版本 |
| 各服务器 `~/.cache/rava/archive/jdk<M>/<B>/` | 解包后的 rlib / rmeta / dylib 与 `manifest.json` | 最近 4 个键，加上正被作业引用的键 |

- 产物包规模：28 例档案的全部 rlib / rmeta 合计 939 MB，`zstd -3` 后 183 MB（5.1 倍，0.86 s）。按类数比例，全集档案约 2.1 GB，压缩后约 0.4 GB / 键。
- 调度方存储上限：2 个 JDK × 8 个键 × 0.4 GB ≈ 6.4 GB；逐例闭包每版本约 215 MB / JDK。
- `manifest.json` 内容：每个文件的 sha256 与大小，加上 `P`、`S`、`B`、`rustc -vV`。它最后写入，写入后改名生效。目录内无 `manifest.json` 即视为不完整。
- 服务器侧路径固定在家目录，不随作业 checkout 目录变化。同一服务器上不同作业、不同 tag 共享。

### 4.3 作业流程

以一次 JDK `<M>` 的全量作业为例。

**阶段 1（闭包，分片并行）**
- 调度方按 `C` 查逐例闭包缓存，只把未命中的测试分片下发。
- 各服务器跑闭包，结果回传调度方存入缓存。
- 回传失败的分片由调度方改派给其他服务器，与今天分片失败的改派相同。

**阶段 2（并集，调度方本机）**
- 调度方以全部逐例闭包为输入，跑多根开放世界分析得到档案，并计算 `P`。
- 命中 `index/<P>` 且对应 `B` 的工具链与目标服务器一致，则直接进入阶段 4。

**阶段 3（档案构建，单构建者）**
- 调度方从当前在线、内存满足要求（进程上限 ≥ 7 GB，现形态声明层峰值约 6.0 GB）的服务器中，按健康度顺序指定一台为构建者。jp2 排在最后。
- 构建者经 `heavy_lock` 生成并编译档案，打包上传调度方，记录 `index/<P>`。
- 构建者由调度方经现有 SSH 轮询监视。连续 3 次轮询失联，或超过「预估构建时长 × 2」，就改派下一台。旧构建者恢复后若上传的 `B` 与已有的相同，丢弃即可。
- 阶段 3 进行期间，其他服务器已经开始做用户 crate 的转译。转译只依赖档案闭包，不依赖编译产物。

**阶段 4（分发与消费，各服务器独立）**
- 本机缓存命中 `archive/jdk<M>/<B>/manifest.json` 并校验通过，直接使用。
- 否则从调度方拉取 `<B>.tar.zst`。

**阶段 5（逐例编译与运行）**
- 只编用户 crate，链接本机档案，见 §4.4。

**并发**
- 同一服务器上多个作业 / 测试进程并发访问同一个 `B` 时，用 `flock(archive/jdk<M>/<B>.lock)` 互斥安装：
  - 第一个进程下载、解包到 `<B>.tmp.<pid>`，校验后改名为 `<B>`；
  - 其余进程等锁后直接使用。
- 读取方只读，不持锁。

### 4.4 本机消费：直接调用 rustc 链接档案

- 用户 crate 不再经 cargo 编译，由 `rava compile` 直接调用 rustc：
  - `--extern java_runtime=<archive>/libjava_runtime.*`（各 body crate、JDK `java_meta` 同理）；
  - `-L dependency=<archive>/deps`。
- 不用 cargo 的原因：
  - cargo 指纹绑定 target 目录与绝对路径，而各服务器 checkout 路径按作业不同，指纹必然失效；
  - §1.6 实测 cargo 对大 rlib 的检查与 build.rs 本身就要约 7 s。
- 档案构建统一使用 `--remap-path-prefix=<构建目录>=/rava/profile`。这保证同一 `S` 在不同服务器上构建出的产物与路径无关，调试信息里的路径也一致。
- 链接方式：
  - **语料模式**：档案编为 Rust `dylib`，用 `-C prefer-dynamic` 并设置 rpath 指向本机档案目录。
    - 单例二进制只含用户 crate，消除了约 350 MB 的单例 debug 二进制与对应的链接耗时。
    - 1061 例共享一份档案，约 2.1 GB / 键 / 服务器。
  - **生产模式**：静态链接，用 `--gc-sections` / `-dead_strip` 裁剪。档案就是项目自身的闭包。
- 用户元数据：用户类的反射 / 注解元数据行生成在用户 crate 内，启动时注册到 JDK `java_meta` 的表中。JDK `java_meta` 属于档案。

### 4.5 链路中断的重试与回退（针对 jp2 一类）

**拉取**
- 调度方经 SSH/SFTP 推送到服务器，复用现有连接：先直连，失败降级代理，退避 2 s → 5 s → 10 s。
- 按 64 MB 分块传输，每块单独校验 sha256，断点续传。已到达的块记在 `<B>.part/` 中，重连后从缺失块继续。

**回退**
- 拉取预算 = min(10 min, 本机构建预估时长)。现形态约 5 min；S7 后约 2–3 min。
- 预算内拉不完，或连续 3 轮重连失败，服务器立即转为本机构建同一个 `S`，得到同一个 `B`，因为工具链一致。
- 本机构建完成后，服务器保留自己的产物，不回传；调度方只记录「jp2 本机构建」。
- 在调度方看来，回退与拉取成功等价，都以 `manifest.json` 校验通过为准。

**完全失联**
- 服务器在阶段 4/5 期间完全失联：调度方按现有分片改派机制把它的剩余测试改派给其他服务器。其他服务器已有档案，改派后立即可编。

**不依赖单机在线**
- 构建者失联改派（阶段 3）；
- 消费者失联转本机构建，或改派它的测试（阶段 4/5）；
- 调度方本身即作业发起者。

### 4.6 一致性校验与 GC

**校验**
- 解包后逐文件核对 `manifest.json` 的 sha256。
- 使用前比对本机 `rustc -vV` 与 manifest 记录。不一致视为未命中，按本机工具链的 `B'` 构建，并上报工具链漂移。

**确定性**
- 档案构建者对 `S` 做两次生成确定性检查，与 `seed_check.sh` 同口径。
- 不同服务器对同一 `S` 的产物不要求逐字节相同：rustc 产物的逐字节可复现不是本方案的目标。只要求 `B` 相同，且用户 crate 链接后行为一致。
- 抽查口径：同一 `B` 在任意两台服务器上跑同一测试，结果相同。

**GC**
- 服务器每次作业结束时清理 `archive/jdk<M>/`，只保留最近使用的 4 个键与正被引用的键。
- 引用登记：作业在 `<B>.refs/<tag>` 下放一个文件，作业结束删除；超过 24 h 未更新视为失效。
- 调度方按 §4.2 的保留数清理。
- 磁盘下限仍按 `MIN_DISK_GB` 守护。

### 4.7 生产（单项目）模式

- 不涉及分发：档案即项目闭包，缓存在开发机的 `~/.cache/rava/archive/jdk<M>/<B>/`，键结构相同。
- 项目源码改动，只要不改变 JDK 侧闭包，就只编用户 crate。改变 JDK 侧闭包时，档案重建一次。

- 逐例生成树中 JDK 类的版本数从今天的最多 18 个（`java/lang/String`）降到 1 个。

### 5.3 实施顺序

前置：C1d、C4 按既定计划先完成（闭包分析器）。档案键的内容摘要依赖分析器输出稳定，分析器仍在大改时档案频繁重建。

1. **生成器：档案模式**
   - 多根开放世界分析：`rava` 接受多个入口的闭包，或直接接受多入口，产出档案闭包与内容摘要。
   - JDK crate 只依赖档案生成。用户 crate 独立生成。`java_meta` 拆为 JDK 表加用户注册行。
   - 验收：同一 `P` 下任意两个用户程序生成的 JDK crate 逐字节相同；全集通过集合与今天一致，不得回退。
2. **驱动：直接 rustc 链接**
   - `rava compile` 对用户 crate 直接调用 rustc，`--extern` 档案。语料模式档案为 dylib。
   - 验收：单例 p50 ≤ 2 s、p99 ≤ 5 s、峰值 ≤ 1 GB；1061 例结果与第 1 步一致。
3. **分发：§四协议**
   - 键、存储、分块续传、拉取预算、本机构建回退、改派、GC，落在 `server_maintenance/rava` 的调度与远端脚本中。
   - 验收：人为断开 jp2 链路，作业照常完成，jp2 走本机构建；全量 ≤ 11 机时。
4. **档案体量：§7.5.4 第 1–7 项，然后 S7**
   - 只影响档案构建（每键一次）与生产模式首次构建，不在逐例关键路径上。

### 6.4 1b 设计（t1-1b，2026-10-04）

**接口**
- `rava build|emit <Main.java> --profile profile.json`：
  - 读档案，校验键输入（生成器摘要、runtime 树摘要、JDK 主版本）与当前一致，不一致报错要求重新 `rava profile`；

  - 单例的非用户类 / 方法 / 调用点引用 / lambda 接口必须被档案覆盖，否则报错（先把本程序并入档案，P 随之改变）。
- 档案新增集合 `sam_types`（lambda 站点的函数式接口，分析器 `Engine::sam_types`），单例 closure.json 同名字段。
- 发射选项 `EmitOptions.archive`：档案 crate 的包版本取内容摘要。
- 运行时：`java_runtime::meta::UserMeta` / `register_user(&'static UserMeta)`；查询入口返回档案侧表与用户侧行合并后的表。

**数据流**
```
profile.json ─┐
              ├─ compose ─ EmitInput ─ write_project ─┬─ 档案 crate：java_runtime / java_body_* / lib crate
单例闭包 ─────┘                                      │    java_meta + closure_input/{meta,closure,line}_tables.rs
                                                     └─ 用户 crate：user/src/*（类）+ rava_user_meta.rs（元数据行）
                                                          main.rs 首句 register_user(&rava_user_meta::USER_META)
```

**改动点**
- 合成与入口：`input/src/compose.rs`（新）、`input/src/facts.rs`（`sam_types`）、`driver/src/profile_emit.rs`（新，读档案并校验）、`driver/src/build_cmd.rs` / `build_opts.rs`（`--profile`）、`closure/src/profile.rs` 与 `closure/src/lib.rs`（`sam_types` 集合）。
- 发射层只让档案事实决定档案 crate 的内容。逐项排查出的用户侧泄漏有四处：
  1. vtable 槽裁剪（`emit/src/vtable_prune.rs`）：非用户类的槽按档案侧事实判定，并按开放世界假想用户子类，即可被用户扩展的类保留可能被覆盖的槽；槽计划与逐方法判定在无作用域视图上求值。原先在首个查询文件的作用域里求值，会把类型名认领进该文件的导入，导致 JDK 文件随用户程序多出 import。
  2. `I__Lambda` 合成集（`emit/src/sam.rs`）：JDK 接口取档案 `sam_types`，用户站点只贡献用户接口。
  3. 继承成员需求（`emit/src/project/archive_side.rs`，新）：档案侧需求只来自三类——手写体需求、`visited` 中属主未声明的实例方法、非用户类发射登记的需求。用户方法体对非用户接收者登记的需求不入账；未被档案侧覆盖时报 `[archive-leak]`，仍入账以保证本程序可编译。
  4. 反射元数据与行表的两侧拆分，见下一条。
- `java_meta` 拆分：
  - 原 java_meta 构建脚本的扫描与渲染逻辑移到 runtime 侧普通库 `runtime/rava_meta_tables`，由发射层调用（与 `rava_macros_core` 同为生成器的 path 依赖）。它含手写根类 Object 的成员行，所以不放进生成器 crate（生成器 crate 不得有 JDK 类名字面量）。
  - 档案侧：扫描 `java_runtime/src` 与 lib crate 的落盘文件，写 `closure_input/meta_tables.rs`，由 JDK `java_meta` 以 `include!` 引入，表 static 以 `__java_meta_<表名>` 导出。`java_meta` 不再有构建脚本，也不再扫描用户 crate。
  - 用户侧：`project/meta_sides.rs`（新）扫描用户类的发射文本，渲染为 `const` 表，加上用户模块服务（服务或 provider 是用户类）和用户文件的栈帧行表，聚合成 `USER_META`，写入 `user/src/rava_user_meta.rs`。
  - 栈帧行表（`project/line_tables`）按文件归属拆分：`user/` 下的文件进用户侧，其余进 `closure_input/line_tables.rs`。模块服务表同样拆分（`entry::write_closure_tables` 只写档案侧）。
  - 运行时 `meta.rs`：每个查询入口经 `merged_table!` 合并两侧。首次查询时合并一次，按类名稳定排序（模块服务保持事实序：档案在前、用户在后）；未登记用户侧行时直接返回档案侧表。
- 包版本（`archive_side::stamp_versions`）：
  - 档案发射时，档案 crate（`java_runtime`、`java_meta`、`java_body_*`、lib crate）的版本统一取 `0.0.<FNV-1a 64>`。摘要覆盖这些 crate 目录的全部文件和 java_meta 引入的三个 `closure_input` 表文件，Cargo.toml 去掉版本行后计入。
  - 同内容才同版本：共享 target 下跨程序复用档案 crate 产物，且不会误用陈旧产物。
  - 单例模式仍取 scratch 路径（`scratch_pkg_version`）。

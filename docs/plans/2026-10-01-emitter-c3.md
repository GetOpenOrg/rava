## 〇、目标（终态）

分析器已经证明的事实，生成器一律照做，不再翻译分析器判定不会执行的代码，也不再为分析器判定不存在的派发发 vtable 槽：

| 项 | 分析器事实（closure.json） | 生成器终态 | 量化 |
|---|---|---|---|
| 1 null_recv | `folds[].null_recv`：接收者值集恒空的活虚调用点 | 该点弹出实参与接收者（副作用按求值序保留），直接抛 NPE；调用本身与其后仅经它可达的代码 0 翻译 | null_recv 点上的调用发射数 = 0 |
| 2 noreturn | `folds[].noreturn_calls` / `noreturn_dead_pcs` | 调用照常翻译，其后控制流终止；`dead_pcs ∪ noreturn_dead_pcs` 0 翻译 | 死区翻译指令数 = 0 |
| 3 consts / 系统属性 | `folds[].consts`；分析器折叠用的系统属性表 | 折叠点发常量（已做）；运行时初始属性表与分析器折叠所用的表同源（`[facts.system_properties]` → closure.json → runtime build.rs） | 手写属性表中的常量项 = 0，未登记键 = 0 |
| 4 class_init | `class_init.{targets, unknown}` | JDK 类按事实登记初始化钩子（与用户类同一张 `CLASS_INIT_HOOKS`）；`Unsafe.ensureClassInitialized` 接 `crate::ensure_class_initialized` | 目标类钩子缺失 = 0 |
| 5 dispatch | 各虚调用点的目标集 | 按分派结果发 vtable 槽：从未被派发到的实现不占槽，无覆盖派发的槽不声明 | 未派发实现的槽条目 = 0 |
| 6 levels | `classes[].level` | L1（名字级）类发不透明类型；接口链断开时由分析器规则把接口升到 L2，发射层不做特判 | L1 类的方法 / 字段发射 = 0 |

约束：生成器 / 分析器代码不出现 JDK 类名字面量（一切走清单与字节码）；不改 `build/` 下的生成文件；不新增环境变量；单文件 ≤ ~600 行。
分析器侧改动单独提交并在第五节笔记标明（closure-prec3 在另一条线继续演进，合并时冲突按终态解决）。

## 二、各项设计

### 1. null_recv：恒 null 接收者调用点抛 NPE

**规范化**（`input::norm`）：`null_recv` 列出的 pc（须为活的 invokevirtual / invokeinterface，否则报格式错）替换为
`NInsn::NullRecv { call }`。CFG 视图（`method::blocks::cfg_view`）把它看作 `athrow`：无正常后继，只连覆盖它的异常处理器——
与 JVM 在该点的行为（抛 NPE，按异常表转移）一致。`CodeOps::ops()` 不再产出该调用指令，被调方不进导入 / 引用扫描。

**翻译**（`instr::sim`）：弹出实参与接收者；实参里有副作用的按求值序保留（接收者有副作用且实参也有时先把接收者绑定到局部变量，
保持「接收者先于实参求值」），然后发

```rust
return Err(__null_recv(&recv, "类.方法:描述符@pc"));
```

`__null_recv` 是运行时 prelude 里的封装（与 `__stub` 同处）：接收者确为 null → `JvmError::null_pointer()`；
不为 null → panic 并报出调用点（见健全性）。形态与 `athrow` 的 `return Err(..)` 一致，try 区间内由 `java_try!` 同样改写为转移到处理器。
不出现禁止清单里的底层调用。

**其后代码**：null_recv 调用的目标集为空，按定义它不会正常返回，与 noreturn 调用同样是控制流终点。分析器把 null_recv 点
并入 `cut_after` 的终点集，`noreturn_dead_pcs` 因此覆盖「只经 null_recv 点可达」的区间（分析器改动，单独提交；
`noreturn_calls` 字段语义不变，仍只列唯一目标不返回的调用）。

**字段访问**：分析器不导出 getfield / putfield 的恒 null 接收者。生成器对非 `this` 接收者已发 `recv.__nn()?`（JVMS §6.5），
null 时抛可捕获的 NPE，行为正确；只在字段按 levels 裁剪（第 6 项）后才需要该事实，届时由分析器导出 `null_field` 同格式条目。

**健全性论证**。null_recv = 「全部克隆里接收者值集没有对象」。值集为空与「恒为 null」等价的前提是：凡能写入该值的来源都被建模。
未建模的写入（手写层写字段而未被 syn 推断、Unsafe 按偏移写入、反射写入）会让值集偏小，此时：

- 被调方法本来就不在调用链上（分析器不给目标入链），按调用翻译也只会命中 `panic!("stub: ..")`；改成 NPE 后，误剪的后果从「存根 panic」变成
  「若接收者实际非 null 则 panic」——`__null_recv` 在运行时核对接收者，非 null 时 panic 报 `null_recv 违约：<调用点>`，**不会把非 null 接收者静默当成 NPE**。
  诊断信息比存根更精确（直接给出违约的调用点，指向分析器缺的写入来源）。
- 其后被 `noreturn_dead_pcs` 剪掉的代码：只有在上一条 panic 之后才可能需要，panic 已终止程序，不存在「静默走错路」。
- 生成期防线：规范化校验 null_recv pc 为活的虚调用指令、与 consts 不重叠；闭包 `--flows @nullrecv` 列出全部点供审计（已有）。

### 2. noreturn：不返回调用后终止控制流

**规范化**：`noreturn_calls` 的 pc 替换为 `NInsn::NoReturn { call }`，CFG 视图同样看作 `athrow`（调用可能抛异常，覆盖它的处理器保留）；
`noreturn_dead_pcs` 与 `dead_pcs` 合并为删除集。合并后的约定（边界收窄 §6.11 项 9）：死区只从跳转 / switch / return / athrow、
noreturn 调用或 null_recv 调用之后开始；其余活指令顺序落入死区仍报格式错。`noreturn_dead_pcs` 内的处理器（只由被剪区间进入）
连同表项删除，不要求列入 `dead_handlers`。

**翻译**：调用照常翻译（副作用与异常传播保留），有返回值则丢弃，然后发 `__noreturn("类.方法:描述符@pc")`（运行时 prelude，返回 `!`）。
被调方若违反分析结论而正常返回，panic 报出调用点；不会继续执行被删掉的代码。

**健全性**：noreturn 判定只针对唯一目标为字节码方法、全部节点已分析、无返回路径的调用（分析器 `noreturn.rs`），不依赖值集完整性；
`__noreturn` 兜底保证违约可见。

### 3. consts 与系统属性表同源

consts 在折叠点发常量已由 `apply_fold`（`FoldField` / `FoldCall` / getstatic 装载）完成，本期不改。

**系统属性**：分析器按 `[facts.system_properties]`（`values` 常量值、`dynamic` 运行期取值的键；两者之外的键视为缺省 null）折叠属性读点。
现状运行时 `system_impl.rs` 手写了一份属性表，与清单是两份真源，已经不一致（`jdk.reflect.useNativeAccessorOnly` 清单为 `"true"`，
运行时缺省 → 分析器剪掉的分支在运行时实际可达）。终态：

1. 分析器在 closure.json 导出 `system_properties: {values: {键: 值}, dynamic: [键…]}`——分析器折叠所用的表原样导出（单独提交）。
2. runtime `build.rs` 读 `../closure_input/closure.json`，生成 `OUT_DIR/system_properties.rs`：`VM_CONST_PROPERTIES`（常量）与
   `VM_DYNAMIC_PROPERTIES`（动态键）。closure.json 相关的 build 逻辑（服务表、属性表与共用的 JSON 小解析器）移到独立文件
   `runtime/java_runtime/build_closure.rs`，overlay 随 `build.rs` 一并复制。
3. `System.registerNatives` 手写层：常量项全部来自 `VM_CONST_PROPERTIES`；动态键逐个经 `dynamic_property(键)` 取宿主值
   （`java.home`、`os.*`、`user.*`、编码族、`java.vm.*` 中随 VersionProps 的键）。手写层不再出现常量字面量属性值，
   也不再能写入清单未登记的键：动态键由清单列出，手写层只提供取值；清单列出而手写层无取值的键不写入（等价缺省 null，与分析器
   「动态 = 不折叠」一致）。

健全性：运行时表 ⊆ 分析器所见的表（常量值逐字相同，动态键不折叠），折叠结论在运行时成立。

### 4. class_init：JDK 类初始化钩子消费分析器事实

`ClosureFacts` 增 `class_init: { targets, unknown }`（`from_closure` / `from_json` 两路）。`emit::project::entry::class_init_hooks`
在用户类、注解枚举之外，为 `class_init.targets` 中「已生成且 `<clinit>` 在链上」的 JDK 类登记钩子（`unknown = true` 时覆盖全部
`clinit` 列表中已生成的类），与现有条目同一张 `CLASS_INIT_HOOKS`，键为 binary name。手写 `Unsafe.ensureClassInitialized(c)`
由 no-op 改为 `crate::ensure_class_initialized(<c 的类名>)`（注释改为按事实分派）。未登记的类（分析器判定不经此初始化）仍是 no-op——
与分析器「只有 targets 进入初始化层」一致。

### 5. dispatch：按分派结果发 vtable 槽

现状：`emit::vtable::find_virtual_in` 对一切实例方法（含 private、不在链上的存根）给出 `virtual_in`，宏为每个声明者生成
`A__VTable` 槽、为每个覆盖者生成 `impl A__VTable for C__inner` 条目；存根覆盖也占槽。

**分析器侧**：closure.json 的 `dispatch` 只导出目标数 > 1 的调用点。按槽判定需要「方法 → 是否是某个虚调用点的目标且经槽到达」。
新增导出 `dispatched: ["类.方法:描述符", …]`：全部活虚调用点（invokevirtual / invokeinterface，含单目标）目标之并，
以及手写层 / 反射经 vtable 调到的实例方法（手写体的回调边、反射成员）。

**生成器侧**：槽的需求按「调用点形态」判定——调用点 `recv.m()` 的静态接收者类型 R 解析到的方法 R.m 所属槽族（最远声明者 A.m 及其全部覆盖者）
里，若存在被派发到的实现不是 R.m 本身，则调用必须经 vtable：

- 槽族需要声明（`virtual_in = A`）⇔ 族内被派发到的实现 ≥ 2，或唯一被派发到的实现不是族根的声明；
- 覆盖者 C.m 占槽（`virtual_in = A` 且 C ≠ A）⇔ C.m ∈ `dispatched`；否则只作为 C 的固有方法（super 调用路由改为固有方法）；
- private 实例方法不占槽（JVMS §5.4.6：private 方法的 invokevirtual 只选中它本身）。

依赖：宏的 `ClassName__m_base` 自由函数只为虚方法生成，invokespecial 路由（`instr::invoke::special`）须对不占槽的方法改走固有方法；
继承成员委托（`phase2/inherited.rs`）对不占槽的祖先方法改为经 upcast 的固有调用。健全性：未派发到的实现不在分派集合 = 分析器判定
没有任何虚调用点会选中它；若分析器漏边，该实现本来就不在链上（存根），改为运行祖先实现前须由 `__stub` 同级的诊断兜底——
不占槽的覆盖者若在链外，其祖先槽的 default 在运行时核对接收者实际类型（见实施笔记，未定前不落地）。

### 6. levels：L1 不透明类型

L1（`level = type`）：只出现在签名 / checkcast / instanceof / catch 中、从未实例化且无已实例化子类，值只可能是 null。
发射形态：一行不透明声明（宏新增 `java_class_opaque!` 形态，宏名以生成标记 `rava_macros::java_class` 开头：同名 struct + `ObjectVTable` null 实现 + `From<Object>`，无字段、无方法、无 vtable trait），
签名与 checkcast / instanceof 照常引用；instanceof 恒 false、checkcast 只放行 null（由分析器在 folds 中作为常量导出，
边界收窄 §6.11 列为 C3 待定项）。

接口链断开（L2 类实现的接口为 L1，而发射层的接口 impl 链需要其载体）时，由分析器规则把接口升为 L2（「已实例化类的超接口至少 L2」），
发射层只按 level 取形态，不做类名特判。L1 类作为 L2 / L3 类的父类不会出现（分析器规则：L2 / L3 的父类至少 L2）。

## 五、实施笔记

### 第 1、2 项：null_recv / noreturn（合并实施）

分析器提交（closure crate，单独提交）：

- 3acf42e0：`noreturn_dead_pcs` 把 null_recv 调用点也当作截断终点；closure.json 增 `system_properties`（第 3 项备用）。
- c64f489a：落在截断区间里的 null_recv / noreturn 终点不再列出。它们已经被前一个终点截断、不可达，发射层按「活调用点」校验会报不一致（例：`BufferedOutputStream.write` 中 `lock.lock()` 截断后，`unlock()` 仍被列出）。
- 2239fb59：落在截断区间里的常量折叠点不再列出（例：`AbstractStringBuilder.append` pc 57）。
- 79dc6e0e：null_recv 调用点不再同时列为常量。目标集为空时返回值格缺席，原先会被当作 null 常量（例：`ServiceLoader$ModuleServicesLookupIterator.iteratorFor` pc 147）；调用只会抛 NPE，所以 null_recv 优先。

发射层改动：

- `input/facts.rs` 读入 `null_recv` / `noreturn_calls` / `noreturn_dead_pcs`（以及第 4 项要用的 `class_init`）。
- `input/norm.rs`：
  - 新增 `NInsn::NullRecv` / `NInsn::NoReturn`，CFG 视图把两者都当作 athrow 终点。
  - 死集合取 `dead_pcs ∪ noreturn_dead_pcs`。
  - 处理器落在截断区间内的异常表项一并删除。
  - 校验：两类调用点都必须是活调用指令，且不与常量折叠点重叠。
- `instr/sim/abrupt.rs`：
  - null_recv：先弹出实参和接收者（有副作用的保留求值顺序），再发 `return Err(__null_recv(&recv, "被调方"))`，不翻译调用本身。
  - noreturn：照常翻译调用，其后发 `__noreturn("被调方")`。
- 运行时 `lib.rs` 新增两个函数（进入 prelude），用来把分析器违约变成显式 panic：
  - `__null_recv`：接收者确为 null 时返回 NPE，非 null 时 panic 报违约。
  - `__noreturn`：被调方返回时 panic 报违约。

验收：

  - noreturn 调用后发 `__noreturn`（例：`BigInteger.reportOverflow`、`Formatter.failMismatch`）。
  - 被截断代码不再引用的 use、继承委托随之消失。
  - `lib.rs` 多了两个运行时函数。
- raw-audit：27 例 raw_expr / raw_stmt 全部下降（如 TestControlFlow 2422/1330 → 2338/1320，TestDateTimeFormat 39101/3399 → 38143/3335），其余计数不变。
- 单例抽查：TestControlFlow、TestZonedDateTime（含 16 处 `__noreturn`）cargo build 通过，运行输出与 JVM 逐字一致。

#### 已知问题：TestStreamAdvanced 的 null_recv 违约（分析器折叠不可靠，待精度线修）

现象：`printf("%.2f")` 处 panic，报「null_recv 违约：`java/util/ResourceBundle.getObject:(Ljava/lang/String;)Ljava/lang/Object;` 的接收者非 null」。调用点是 `getObject@22`，即 `parent.getObject(key)`。第 5 项改动前的树（`build/c3-sp`）同样会 panic，与槽裁剪无关。第 1 项消费 null_recv 之前，这里按普通虚调用发射，所以问题一直没暴露。

真实 JVM 下接收者不是 null：
- 用反射探针读 `getNumberFormatData(en_US)` 束链，得到 `FormatData_en`（本身没有 `DefaultNumberingSystem`），其 parent 为 `FormatData`（有该键，值 `latn`），后者的 parent 为 null。
- `getNumberStrings` 里 `rb.getString("DefaultNumberingSystem")` 必然经过 `getObject@22`，此时接收者是非 null 的 `FormatData`。
- 结论：生成器发射没有问题（违约检查按设计触发），分析器推出 null 是错的。

根因（closure crate）：
1. `ResourceBundle.parent` 只在 `setParent` 中写入。`setParent` 的回调边由 `locale_resources_impl.rs` 的 `#[jvm_boundary(upcalls = "…setParent…")]` 声明，实际调用在私有 helper `__bundle_chain` 里，形如 `chain[i].setParent(Clone::clone(&chain[i + 1]))`。`close_transitive` 已把这个调用并入宿主方法。
2. `engine/hw_syntax.rs` 的 `hw_type`：实参的静态类型是抽象类 `ResourceBundle`，返回 None。于是 `hw_args` 退回宿主方法的值池 `Node::S(m, POOL)`。
3. 宿主方法的值池只含 P0、手写分配 / 构造和回调返回值。束对象由 `crate::data_bundles::lookup(name)` 的函数指针构造，这在语法上不可见。`engine/seeds.rs` 的 `seed_locale` 只对束类做 `instantiate`、`init` 和 `seed_method(<init>)`，不把束对象作为值产出到任何节点。
4. 结果：`setParent` 的 P0（接收者）经 `open(ResourceBundle)` 展开后含各束，但 P1（实参）为空集。`ResourceBundle.parent` 字段因此为空，`getObject@18` 的 getfield 为空集，`@22` 被判为恒 null。`ResourceBundle.handleKeySet` 的 `null_recv [32]` 很可能同源，待精度线一并复核。

#### 第 5 项修订：槽按实例化类的实际选中实现保留，未分派到的实现发存根

上一版的健全性缺口：槽是否保留直接看 `dispatched`。分析器漏一条派发边时，被漏的覆盖者不占槽，运行时悄悄执行祖先实现，不报错。修订后槽的保留与 `dispatched` 无关，`dispatched` 只决定槽条目是方法体还是存根。

**构造**（`emit/src/vtable_prune.rs`；分析器 closure.json 已导出 `instantiated`，input 侧新增 `EmitInput.instantiated`）：

- 有效声明者：对每个已实例化的具体类 X，沿超类链取每个槽族里 X 实际选中的实现所在类（JVM 选择语义，只看类层次，不看分派结果）。
- 族需要槽 ⇔ 族里存在不在族根的有效声明者。
- 族根在需要槽的族里保留槽。覆盖者 C.m 保留槽 ⇔ C 自己或 C 的某个严格子类是有效声明者。
- 保留槽的有效覆盖者若不在 `dispatched` 里，发 `slot_stub = "true"` 属性：
  - 宏 VirtualOverride 的槽条目改发 `__stub("stub: 类.方法:描述符")`。
  - 继承成员（`vtable_owner` 填槽）的转发体同样改为存根，且不导入 `_base`。
  - 方法本身照常翻译：`C__m_base`、wrapper 上的方法、`__impl_m` 不变，super 调用和精确类型调用不受影响。
- 强制保留不变：Object 方法、族根不声明、合成或桥方法、手写参与。这些情况既不裁剪也不发存根。

**为何漏派发必然显式失败**：

1. 运行期对象只可能是已实例化类的实例。`instantiated` 来自可达方法体里的 `new` 指令，以及反射、服务、种子、手写层清单声明的分配点。它是语法层面的事实，不依赖类型流精度；分配点所在的方法若不可达，其方法体就是存根，执行到会先 panic。
2. 不需要槽的族：所有实例化类选中的都是族根实现，直接调用族根与 JVM 选择一致，不存在可漏的覆盖。
3. 需要槽的族：调用经 vtable 到达接收者实际类的槽条目，条目就是该类实际选中的实现。
   - 该实现在 `dispatched` 里：执行方法体。
   - 不在：执行存根，panic 报出类名、方法名、描述符。
   - 任何情况下都不会落到祖先实现。
4. 覆盖者 C 不保留槽（C 及其子类都不是有效声明者），说明没有任何实例化类选中 C.m。所以 C.m 只能经 invokespecial 或精确调用到达，这些路径不走槽。

健全性的前提从「派发边完整」收窄为「实例化集合完整」。后者是语法事实，分析器另有 `--strict` 和 dyn_compare 的类粒度核对兜底。

#### dyn_compare 方法粒度对照（mmiss）对 dispatched 的覆盖与门禁建议

**现状**（main 上的 `scripts/dyn_compare.py` `compare_methods`，agent 的 MethodEntry 事件）：

- 判据：程序期首次进入某方法时，调用方帧是翻译体（字节码方法或 cut 截断体），而被调方不在 closure.json 的 `methods` 里，记为 mmiss。
- JVM 的 MethodEntry 报的是实际选中的实现（声明类.方法:描述符），与 `dispatched` 的三元组同一口径。所以虚调用点上被漏掉的实现，只要从未进入 `methods`，mmiss 就能报出来。

**盲区**：mmiss 拿来比对的是 `methods`（可达方法），不是 `dispatched`。两种漏派发边它看不到：

1. 实现经别的路径可达。例如 C.m 经 super 调用或精确类型调用进入了 `methods`，但虚调用点到 C.m 的派发边漏了。此时 `C.m ∈ methods` 而 `C.m ∉ dispatched`。本项修订后，这种情况在原生程序上会落到槽存根。
2. agent 只记录每个 jmethodID 的首次进入。如果首次进入走的是 invokespecial 或 static 路径，之后的虚派发进入不会出现在事件里。

**补齐方式（终态）**：

- agent 的 M 行增加调用点指令种类：从 caller 帧的 bci 读出 invokevirtual 或 invokeinterface。
- 去重键改为 (被调方, 调用种类)。
- `compare_methods` 增加一条判据：调用种类是虚调用，且被调方 ∉ `dispatched`（排除接口 default 与 hwobj 方法，与分析器 `dispatched` 的导出口径一致），记为 `dmiss`。
- 这样每条运行期实际发生的派发边都与 `dispatched` 逐条对齐。

**门禁建议**：把翻译域内的 mmiss（含补齐后的 dmiss）升为 run_tests 的硬门禁。

- 失败的确定性：翻译域 mmiss 必然对应原生程序上的存根 panic。槽存根和方法体存根两种都是确定性的，不是诊断噪声。
- 门禁的增量价值：漏派发在原生程序上同样会以 panic 失败（本项的构造保证）。但 dyn_compare 在 cargo 之前就能给出精确的漏边，包括调用点和被调实现，不需要构建 Rust，归因也直达分析器。
- `caller_cut` 的 mmiss（调用方是边界截断体）：被调方经截断体到达，分析器按规范本就不展开截断体，这类 mmiss 不是漏边，而是截断过渡类的规模。单独计数，终态为 0，与边界收窄同口径；门禁报告列出，不计入硬失败。
- 由协调方修改 run_tests，本分支不改。

**现象**：`tests/e2e/23_algorithms/Currency.java` 编译报 E0061，位置 `java/text/decimal_format_symbols.rs`。调用点写的是 `this.__get_currency().getSymbol(locale)`，而 `java/util/currency.rs` 里这个重载按完整重载集合发射为 `getSymbol_locale`，两边对不上。

**根因**：
- `instr::invoke::virtual_` 取重载名时，用接收者擦除类型的 Rust 短名（`erased_head`，此处是 `Currency`）调 `mangle_if_overloaded`。
- `mangle_uncached` 先把 `cls` 当 binary 名查注册表。默认包用户类的 binary 名恰好也是 `Currency`，于是查到了用户类，按用户类的重载集合（没有 `getSymbol`）取名，得到裸名。
- 短名表本身没有歧义：组内字典序最小者 `Currency`（用户类）保留简单名，JDK 类改名 `java_util_Currency`。错误在于把短名当成 binary 名使用。
- 定义侧没有问题：`hierarchy_overloaded_names` 按类文件的完整方法集合计算，不看已发射的子集。

**修法**：虚调用点改用接收者擦除类型的 binary 名（新增 `erased_binary`）求重载名。这样调用点与定义点都从同一个类的完整重载集合取名。其余 `mangle_if_overloaded` 的调用方经排查，传入的都是 binary 名（static / special / ctor / boxing / cross 导入 / 接口），没有同类问题。

**验证**：
- Currency 生成后调用点为 `getSymbol_locale`，构建通过。
- 运行时在 `ResourceBundle.getObject@22` 报 null_recv 违约。这是第 1、2 项笔记里已知的分析器缺陷（`setParent` 实参经值池丢失），与 TestStreamAdvanced 同源，由精度线修复，合入 rust-closure-analyzer 后复测。
- 27 例生成树（`build/c3-dp6` 对照 `build/c3-dp5`）：Rust 源码逐字节相同（closure.json 只有计时统计不同），raw-audit 全等。验收集里没有默认包类与 JDK 类同简单名的情形。

#### L1 静态类型接收者访问 L2 祖先成员：发射侧上转（补到终态）

来源：javac 对上转（`((Base) p).tag`、`((Base) p).id()`）不发 checkcast，字段 / 调用属主是 Base（L2），而栈上
接收者的 Rust 静态类型仍是局部变量的 L1 类 Phantom。分析器侧无法禁止 L1 类作局部 / 参数 / 返回值类型（那正是 L1 的定义），
故选发射侧上转：
- `instr/src/opaque.rs`：`receiver_view`——接收者擦除类型是不透明类、目标（调用属主 / 字段声明类）是它的非不透明真祖先 →
  视图类型（类型实参全取 Object）；`upcast_text` 生成 `Into::<Base>::into(Clone::clone(&p))`（不透明宏对每个传递超类型
  都有 `From<S> for Anc`，null 保持 null，随后 `__nn()?` 照常抛 NPE）；`field_declarer` 沿父类链找实例字段声明类。
- `InstrHooks::is_opaque`（emit 侧按 `EmitInput.opaque` 应答）；invokevirtual 在早期接收者路径之前、getfield / putfield 在
  类型变量上界视图之后改写接收者。invokeinterface 属主是接口：L1 类的超接口若有实现类必为 L2，经同一 upcast 规则；
  属主为 L1 的调用由分析器导出 null_recv，不进这里。
- 同时补上折叠 null 常量作接收者的缺口：`norm` 把折叠 null 换成 `aconst_null`，栈上只剩 `Object` 类型，字段访问
  `Object::default().__nn()?.__get_tag()` 无访问器（E0599）。getfield / putfield 遇空引用字面量接收者 → 声明类的 null
  `<OpaqueLevels_Base>::default()`，`__nn()?` 抛 NPE。（虚调用的同类接收者已由分析器 null_recv 截走。）
- driver 夹具 `OpaqueLevels.java` 覆盖：L1 局部 Phantom 经 `(Phantom) cells[0]` 得到，`((Base) p).tag` 读 / 写走上转；
  `((Base) p).id()` 分析器判恒 null → null_recv；`nobody.tag` 读 / 写（折叠 null）走声明类 null；输出与 JVM 逐行一致。
  断言见 `build_cli.rs::name_level_classes_emit_opaque`。
合入 prec3 时 `engine/fold.rs::null_recv` 预计冲突（prec3 改未建模来源），两侧规则并存：L1 属主恒 null 与值集判空取或。

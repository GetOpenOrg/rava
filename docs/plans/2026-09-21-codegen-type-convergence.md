## 一、诊断：三个形态，一个根因

### 三个形态（2026-09-21 实测）

| 形态 | 实测 | 典型样本 |
|---|---|---|
| **① 擦除-恢复循环** | Object 边界往返发射 30 处、`Into::`/`__into_super` 链 25 处 | 「先上转到精确祖先，再经 Object 边界重新实例化」「经宏为类型形参补的 `From<Object>` 取回（与 areturn 同规则）」——同一对象在一条表达式里装箱→拆箱→再装箱 |
| **② 字符串类型手术** | `split('<')[0]` 类文本分析 37 处；`RawExpr/RawStmt` f-string 拼接发射 140 处 | 类型在 codegen 里是 `str`，子类型关系、泛型实参、接口归属全部靠文本推导，21 个文件各自推导一遍 |
| **③ 特例 if 链** | `coerce.py` 31 + `invoke_sig.py` 88 个条件分支（`_coerce_arg` 一条链 ~15 个语义场景） | 每个分支一条注释解释一个 Java↔Rust 失配场景；知识散落在发射点注释里，而不是类型模型里 |

### 根因

**生成器在错误的抽象层工作**，具体两层：

1. **表面类型缺位**（L2 层问题）：Java 的接口继承/擦除/协变在生成的 Rust 类型位置上没有直接对应物（接口与类型变量位置被擦成 `Object`），于是每个调用边界（实参/返回/字段/接收者）都需要发射点手工补转换。类型系统不做的子类型化，Python 用 if 链补——形态①③的大半下游。
2. **类型推理在字符串空间**（L1 层问题）：没有类型化的中间表示，类型决策（这是什么？能否上转？是不是同族？）在 21 个消费点用字符串模式匹配各自重 derive，发射用 f-string 拼 Rust 源文本——形态②的全部、形态③的剩余部分。

「不自然」的准确表述：**Python 在手工做 rustc 和类型模型本来该做的事**。每修一个测试就多一条 if 分支，是因为修复落在发射点（症状层），而失配的根源在类型系统（架构层）——这正是「架构问题优先」纪律要拦截的累积模式。

### 反例证明（这条路走得通）

A-3（CastExpr IR 化）是完整样板：checkcast/instanceof 从「15+ 处字符串 downcast 匹配」收敛为类型化 IR 节点 + 单一 `render_cast`，12 处字符串发射归零删除，S-1（CCE 可捕获）顺带落地。**模式 = 挑一个转换族 → IR 化 → 闭包指纹验证 → 删字符串路径。**

## 二、终态目标（量化）

| 度量 | 现值（2026-09-21） | 终态 |
|---|---|---|
| 类型字符串手术（`split('<')` 类） | 37 处 | **0**（类型查询全部经类型对象） |
| `RawExpr/RawStmt` 字符串发射 | 140 处 | **0**（全部为类型化 IR 节点；render 层只做节点→文本的单向渲染） |
| `_coerce_arg` 特例分支 | ~15 个场景 | **个位数**（只剩真语义转换：装箱/拆箱、隐式数值拓宽） |
| Object 边界往返（擦了再恢复） | 30 处 | **0**（类型位置载体化后无需往返） |
| `downcast_ref`/`from_any`/`.downcast`（可读层） | 数千处（TSB 859 起） | **0**（A-2 验收口径） |
| 参与类型决策的文件 | 21 个 | **≤3**（类型模型 + 宏 + render） |
| Python 中的 JVM→Rust 类型映射 | `type_map.py` 423 行 + 散布 | **0**（M-3：宏从 `#[descriptor]`/`#[generic_signature]` 自行决策，Python 只传字节码原始字符串） |

## 四、与现行队列 / Rust 重写决策的衔接

- 现行队列不动：数组视图族（在跑，L2/L3 的一个转换族）→ downcast 链（L4-a）→ S-19 剩余 → A-5/A-6/**A-4**（L2-a）→ **窗口 3 + T-1 + M-3 试点**（L1/L3 主战场）。
- 与 Rust 重写的关系：重写决策的门槛是「65/65 + 窗口 0–3 + P-1/G-4」。本文的收敛（尤其 L1）正是给重写**写规格**——TypeIR 的类型代数与 M-3 的宏契约，就是 Rust 生成器的类型系统与接口定义。收敛做透，重写从「重写 19k 行 Python」缩小为「按规格移植类型模型 + 宏」。
- 顺序原则：**每一步都让某些 if 分支失去存在理由后删除它们**（分支数下降是每层的验收），禁止只搬运特例。

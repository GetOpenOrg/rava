## 一、诊断：三个形态，一个根因

### 三个形态（2026-09-21 实测）

| 形态 | 实测 | 典型样本 |
|---|---|---|
| **① 擦除-恢复循环** | Object 边界往返发射 30 处、`Into::`/`__into_super` 链 25 处 | 「先上转到精确祖先，再经 Object 边界重新实例化」「经宏为类型形参补的 `From<Object>` 取回（与 areturn 同规则）」——同一对象在一条表达式里装箱→拆箱→再装箱 |
| **② 字符串类型手术** | `split('<')[0]` 类文本分析 37 处；`RawExpr/RawStmt` f-string 拼接发射 140 处 | 类型在 codegen 里是 `str`，子类型关系、泛型实参、接口归属全部靠文本推导，21 个文件各自推导一遍 |
| **③ 特例 if 链** | `coerce.py` 31 + `invoke_sig.py` 88 个条件分支（`_coerce_arg` 一条链 ~15 个语义场景） | 每个分支一条注释解释一个 Java↔Rust 失配场景；知识散落在发射点注释里，而不是类型模型里 |

### 根因

**生成器在错误的抽象层工作**，具体两层：

1. **表面类型缺位**（L2 层问题）：Java 的接口继承/擦除/协变在生成的 Rust 类型位置上没有直接对应物（接口与类型变量位置被擦成 `Object`），于是每个调用边界（实参/返回/字段/接收者）都需要发射点手工补转换。类型系统不做的子类型化，Python 用 if 链补——形态①③的大半下游。
2. **类型推理在字符串空间**（L1 层问题）：没有类型化的中间表示，类型决策（这是什么？能否上转？是不是同族？）在 21 个消费点用字符串模式匹配各自重 derive，发射用 f-string 拼 Rust 源文本——形态②的全部、形态③的剩余部分。

「不自然」的准确表述：**Python 在手工做 rustc 和类型模型本来该做的事**。每修一个测试就多一条 if 分支，是因为修复落在发射点（症状层），而失配的根源在类型系统（架构层）——这正是「架构问题优先」纪律要拦截的累积模式。

### 反例证明（这条路走得通）

A-3（CastExpr IR 化）是完整样板：checkcast/instanceof 从「15+ 处字符串 downcast 匹配」收敛为类型化 IR 节点 + 单一 `render_cast`，12 处字符串发射归零删除，S-1（CCE 可捕获）顺带落地。**模式 = 挑一个转换族 → IR 化 → 闭包指纹验证 → 删字符串路径。**

## 四、与现行队列 / Rust 重写决策的衔接

- 现行队列不动：数组视图族（在跑，L2/L3 的一个转换族）→ downcast 链（L4-a）→ S-19 剩余 → A-5/A-6/**A-4**（L2-a）→ **窗口 3 + T-1 + M-3 试点**（L1/L3 主战场）。
- 与 Rust 重写的关系：重写决策的门槛是「65/65 + 窗口 0–3 + P-1/G-4」。本文的收敛（尤其 L1）正是给重写**写规格**——TypeIR 的类型代数与 M-3 的宏契约，就是 Rust 生成器的类型系统与接口定义。收敛做透，重写从「重写 19k 行 Python」缩小为「按规格移植类型模型 + 宏」。

## 六、不稳定耦合的应对策略（2026-09-21 增补）

> 背景：用户观察「修一个错改一处逻辑，又引起另一处问题，改不动了」。项目史四次同款事故：K-6 朴素泛化 15 错回退、wt-fix01 签名补闭包闭包膨胀 4 倍撤销、wt-fix01 结构化器单前驱修复致 E0426 回退、G-9 运行时化暴露槽位定型缺陷按纪律回退。

**诊断**：耦合来源不是单块代码质量，而是——①隐式共享状态（StackSim 的字符串+hint 类型事实无唯一事实源，改一个生产者 N 个消费者跟着变）；②字符串空间推理（无编译器可查的不变量，耦合不可见）；③承重 if 链（分支为测试承重且有序，同架构重写只会原样搬运）。另有真语义交互（G-9×G-3 型）——架构无法消除，只能显式化到一处。**结论：重写"丑的那块"无效；有效单元是转换/推理族的升维。**

**处方（五条）**：

1. **G-4 提级现在做**（解锁键）：输出确定 → 「同输入生成树 diff」成为零成本回归网，改造前录指纹、改后 diff，耦合当场现形。小时级投入，给整个收敛阶段装安全网。
2. **改造单元 = 转换/推理族 → 类型化表示**（A-3 样板）：类型化节点 → 逐消费方迁移（指纹护航）→ **删除字符串旧路径**（双路径并存期耦合翻倍，删除是关键）。
3. **惯犯块提取纯函数核 + golden 单测**：`_coerce_arg`（coerce.py/invoke_sig.py）、`stack.py` store_local（K-6 死循环现场）、`sim/fields+methods` 接收者定型、`vars.py`——按输入→输出契约抽纯函数独立测试，同时是 Rust 移植预制品（纯核 ≈ 未来 crate 函数）。
4. **耦合登记纪律**：「修 A 坏 B」记 remaining-issues 耦合对，族重写时两侧一起覆盖，防不同代理反复重新发现同一耦合。
5. **顺序不变**：窗口 3（隐式状态显式化）仍在功能队列后；G-4 与纯核提取随时可插。

**判断标准**：改不动的感受应随承重 if 链的逐族塌缩而消失；若某族升维后仍反复出问题，说明该族该直接进 Rust crate 定型（提前触发重写方案的对应移植单元，golden diff 护航）。

> **2026-09-21 晚外部分析评审吸收**（另一会话对本文档的交叉核对，四处采纳、一处驳回）：
> 1. **采纳——度量数字已失真，L5-b 从"候选"提级为第一件事**：全形态口径实测 Raw 发射 **187** 处（本文此前 140 为 f-string 口径，低估）；所有度量靠人工统计必漂移。**阶段 A（装仪表，1-2 天）**：G-4 确定性 + `RawExpr/RawStmt/TypeSurgery` 计数审计上线，基线 187/37，趋势只降不升。
> 2. **采纳——L1-a 口径再修正（对"完全体只在 Rust"的部分推翻）**：Python 侧必须有**最小 JvmType 语义层**（类型代数 + `erasure()/is_subtype_of()/substitute()` + registry 缓存，约 300 行）——没有它，coerce/转换族无法在 Python 侧升维（阶段 B 的前置），搬 Rust 等于原样搬运。它**不是弃件**：就是 Rust `ty` crate 的规格本体，照抄即可。完全体（全部查询方法 + TypeFacts 不可变化）在 Rust 定型。
> 3. **采纳——处方 3（惯犯块纯核提取）提级到第 1 位**：与 R1 拆库同级的「现在做、Rust 时代全额继承」投资。
> 4. **采纳——新实证补充**：`CastExpr.target` 仍是 `str`（rs_ir.py:208，注释自认"目标 Rust 类型串（含泛型实参）"）——A-3 节点化了但**类型载荷未升维**，是"IR 里藏字符串"的新形态，列为下一个族升维的直接目标。

> **2026-09-23 第二次外部分析复核（erased 逻辑专项）——四处采纳**：
> 1. **理论边界显式化**：「擦除表示与类型化静态层之间的边界是架构故意保留的二元结构，值经过边界的转换永远存在且分散在每个边界位置；能集中且正在集中的是决策（唯一类型模型回答）与表示（类型化 IR 节点）」——此为本文隐含前提的最好表述，提升为正式表述。

> 3. **顺序显式化**：TypeIR 批次 3（invoke_sig×5 + invoke_virtual×4，剩余手术大头）排 a4b6 合入 + compile 族攻坚后、M-3 前——invoke_sig 在 a4b6 域，批次 3 必须等其落地。

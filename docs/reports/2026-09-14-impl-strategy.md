# Java → Rust 转译器：实现策略决策报告

生成时间：2026-09-14  
数据来源：`scripts/trace_callchain.py`（HelloWorld 调用链分析）+ `scripts/scan_jdk_boundary.py`（全 JDK 扫描）

---

## 一、问题背景

Java 标准库（JDK）的公开 API（`java/`、`javax/`）存在两类无法直接翻译的方法：

1. **ACC_NATIVE 方法**：无字节码，直接调用 JVM 本地实现
2. **边界方法**：有字节码，但其中直接调用了 `sun/`、`jdk/internal/` 等内部包

本报告以两个脚本的分析数据为依据，回答以下决策问题：

- 应该选哪种翻译边界策略？
- 需要手写的 native 实现有多少？
- 实现顺序如何安排才能以最小投入解锁最多功能？
- 哪些是真正的风险点？

---

## 二、调用链规模：策略选择的依据

**数据来源：`trace_callchain.py` 对 HelloWorld 的分析**

| 策略 | 类数 | 方法数 | native 边界 | 说明 |
|------|-----:|-------:|------------:|------|
| 单程 RTA（基准） | 687 | 4,054 | 79 | 虚调用保守展开，过估 |
| Two-pass RTA | 635 | 3,124 | 76 | 更准确的基准 |
| VTA + Two-pass | 625 | 3,140 | 74 | 进一步精确虚调用 |
| 跨方法返回类型传播 | 621 | 3,091 | 74 | 效果边际递减 |
| 手动截断（11 类） | 612 | 3,053 | 73 | 小幅改善 |
| **内部包边界截断** | **111** | **366** | **20** | **效果量级不同** |

**关键发现：** 内部包边界截断将规模从 635 类压缩到 **111 类（减少 83%）**，不是渐进优化，是策略性收益。

### 调用链深度分析

HelloWorld 的调用链最深达深度 40，在深度 12-20 出现类数爆炸（每层新增 17-36 个类）。这说明：**调用链膨胀的根本原因不是虚调用分散，而是调用深度**——每一层调用都会带入新的依赖类。内部类（`sun/`、`jdk/internal/`）本身也存在深度很大的调用链，是膨胀的"放大器"。

**策略结论：内部包边界截断是正确方向。** 不翻译内部类的字节码，而是在内部包边界手写 native 实现，将翻译范围限定在公开 API 层。

## 三、全 JDK 量化分析

**数据来源：`scan_jdk_boundary.py` 全量扫描（7,784 个公开 API 类）**

### 3.1 公开 API 的可翻译性分布

| 类型 | 数量 | 占比 |
|------|-----:|-----:|
| **纯字节码（可直接翻译）** | **68,749** | **92.3%** |
| native 方法（JVM 原生） | 388 | 0.5% |
| 边界方法（调用内部包） | 5,314 | 7.1% |
| **需要手写 Rust 合计** | **5,702** | **7.7%** |

> 整个 JDK 公开 API 中，**92.3% 的方法可以从字节码直接翻译**，只有 7.7% 需要手写。
> 这证明"字节码翻译 + 内部包边界手写"的策略是可行的，工作量在可控范围内。

### 3.2 5,314 个边界方法的分布热点

被公开 API 最多引用的内部包（引用次数代表"如果实现这个包，能解锁多少方法"）：

| 内部包 | 被引用次数 | 涉及内部类数 |
|--------|----------:|------------:|
| `sun` (其他) | 2,788 | 208 |
| `jdk/internal` (其他) | 2,511 | 160 |
| `jdk/internal/misc` | 2,256 | 15 |
| `sun/util` | 1,620 | 36 |
| `com/sun` (其他) | 1,436 | 96 |
| `sun/security` | 980 | 72 |
| `jdk/internal/reflect` | 208 | 6 |
| `sun/reflect` | 162 | 18 |

**`jdk/internal/misc` 以 15 个类承载了 2,256 次引用，是最高密度的核心包。** 其中 `Unsafe` 一个类就被引用了 1,379 次。

## 四、内部类方法可实现性：手写量远比预期少

**数据来源：`scan_jdk_boundary.py` 对 654 个内部类的方法扫描**

654 个被公开 API 引用的内部类共有 10,358 个方法，分类如下：

| 类型 | 数量 | 占比 | 说明 |
|------|-----:|-----:|------|
| 纯字节码（无内部依赖） | 6,057 | 58.5% | ✅ 可直接翻译 |
| 有内部依赖（同集合内） | 1,721 | 16.6% | ✅ 依赖实现后可翻译 |
| **小计：可翻译** | **7,778** | **75.1%** | |
| ACC_NATIVE | 139 | 1.3% | ❌ 必须手写 Rust |
| 外部内部依赖（更深层） | 1,815 | 17.5% | ⚠️ 需进一步跟踪 |
| **小计：需手写** | **1,954** | **18.9%** | |
| 抽象/接口 | 626 | 6.0% | — 由子类实现 |

**核心结论：内部类本身 75% 的方法也是字节码，可以继续翻译。** 并不是说"凡是内部类就全部手写"——只有真正的 ACC_NATIVE 方法（139 个）以及调用了更深层内部类的那部分（1,815 个）才需要手写。

### 重要案例：`jdk/internal/misc/Unsafe`

| 项目 | 数值 |
|------|-----:|
| 被引用次数（最高单类） | 1,379 次 |
| 总方法数 | 409 |
| ACC_NATIVE（必须手写） | 84（21%） |
| 有字节码（可翻译） | 325（79%） |

`Unsafe` 通常被认为是最复杂的内部类，但实际上 **79% 的方法有字节码可翻译**，只有 21% 的方法需要手写原子操作/内存操作的 Rust 实现。

## 五、分阶段实现规划

**数据来源：`scan_jdk_boundary.py` 拓扑排序阶段分析**

654 个内部类按依赖关系分为 6 层 + 1 个循环依赖组：

| 阶段 | 类数 | 手写方法 | 可翻译方法 | 解锁边界方法 | 累计进度 |
|------|-----:|-------:|----------:|------------:|--------:|
| **1（叶子层，无内部依赖）** | **349** | 728 | 2,243 | 1,482 | **27.9%** |
| **2（依赖阶段1）** | **68** | 340 | 1,263 | 1,557 | **57.2%** |
| 3 | 42 | 99 | 512 | 399 | 64.7% |
| 4 | 24 | 138 | 379 | 218 | 68.8% |
| 5–6 | 13 | 51 | 147 | 86 | 70.4% |
| **循环依赖组** | **158** | 598 | 3,234 | 1,572 | **100%** |

### 各阶段高价值目标（按被引用次数）

**阶段 1（先实现这些，全部无内部依赖）：**

| 内部类 | 被引用次数 | 手写方法数 | 翻译方法数 |
|--------|----------:|----------:|----------:|
| `jdk/internal/util/Preconditions` | 537 | 1 | 15 |
| `jdk/internal/misc/InternalLock` | 184 | 0 | 7 |
| `sun/security/util/Debug` | 204 | 1 | 20 |
| `com/sun/jmx/defaults/JmxProperties` | 704 | 0 | 1 |
| `com/sun/jmx/remote/util/ClassLogger` | 237 | 0 | 43 |

**阶段 2（最关键，含 Unsafe）：**

| 内部类 | 被引用次数 | 手写方法数 | 翻译方法数 |
|--------|----------:|----------:|----------:|
| `jdk/internal/misc/Unsafe` | **1,379** | 84 | 325 |
| `jdk/internal/org/objectweb/asm/MethodVisitor` | 341 | 0 | 34 |
| `jdk/internal/reflect/Reflection` | 138 | 3 | 19 |
| `sun/util/locale/BaseLocale` | 51 | 0 | 11 |

**实现节奏建议：**
- 先完成阶段 1（349 个类），解锁 27.9% 的边界方法
- 再实现阶段 2（68 个类，核心是 `Unsafe`），累计解锁 57.2%
- 这两个阶段合计 417 个内部类，就能解锁超过一半的边界方法
- 循环依赖组（158 个类）留在最后，它们互相依赖，需要一次性打包实现

## 六、外部内部依赖：潜在风险

内部类方法中有 **1,815 个（17.5%）** 调用了不在 654 个种子类范围内的更深层内部类。这意味着：

- 当前的 654 个种子类并不构成完整的依赖闭包
- 实现这些方法时，会发现它们还需要更多内部类
- 需要再做一轮递归扫描，将这些"第二层"内部类也纳入分析

**这是已知的最大风险**，但不是未知的——脚本已经识别出了这个边界。处理方式：
1. 对 1,815 个"外部内部依赖"方法中，按调用频次筛出最重要的一批深层内部类
2. 将它们加入下一轮种子集合，扩展分析范围
3. 循环直到依赖闭合

---

## 七、循环依赖组（158 个类）

循环依赖组包含 ASM 字节码操作框架（`jdk/internal/org/objectweb/asm`）、反射基础设施、安全框架等相互引用的类。它们：

- 必须整体打包，不能单独分阶段实现
- 包含 598 个需手写方法 + 3,234 个可翻译方法
- 解锁最后 1,572 个边界方法（完成后达到 100%）

**这些类的特点：** 字节码操作类（ASM）在翻译器本身运行时不需要（翻译器是 Python 写的），反射基础设施在 Rust 中有对应机制替代。这个组的优先级可以放低，待前 6 层实现后再处理。

---

## 八、HelloWorld 专项：最小可运行路径

**数据来源：`trace_callchain.py` + 内部包截断模式**

采用内部包边界截断策略后，HelloWorld 运行只需：

| 项目 | 数量 |
|------|-----:|
| 公开 API 类 | 86 |
| 引用类（常量、接口等）| 25 |
| 合计 | 111 |
| 方法数 | 366 |
| native 边界方法（需手写） | 20 |
| 其中边界方法（调内部类）| 207 个，涉及 64 个公开 API 类 |

**207 个边界方法按内部类热点分组：**

| 内部类 | 被 HelloWorld 调用链引用次数 |
|--------|---------------------------:|
| `jdk/internal/misc/Unsafe` | 多（ConcurrentHashMap 等） |
| `jdk/internal/util/Preconditions` | 多（String、AbstractStringBuilder） |
| `jdk/internal/util/ArraysSupport` | 多（String、ArrayList） |
| `jdk/internal/misc/InternalLock` | 多（PrintStream） |
| `jdk/internal/reflect/Reflection` | 中（Class） |
| `jdk/internal/reflect/ReflectionFactory` | 中（Class） |

只需实现这几个核心内部类，HelloWorld 就可以运行。

## 九、决策矩阵

| 决策 | 推荐选项 | 依据 |
|------|---------|------|
| **翻译边界策略** | 内部包边界截断 | 635→111（-83%），不是渐进优化 |
| **最小化 HelloWorld 路径** | 优先实现上述 6 个核心内部类 | 覆盖 207 个边界方法的主体 |
| **内部类实现方式** | 先翻译字节码，只对 ACC_NATIVE 手写 | 内部类 75% 有字节码，手写比例仅 18.9% |
| **实现顺序** | 阶段 1（叶子层）→ 阶段 2（Unsafe 等）→ 循环组 | 前两阶段 417 类解锁 57% 边界方法 |
| **全 JDK 覆盖** | 阶段性推进，不必一次完成 | 7.7% 方法需手写，其余 92.3% 可翻译 |
| **循环依赖组处理** | 放最后，整体打包 | 158 类互相依赖，无法单独拆分 |
| **"外部内部依赖"处理** | 下一轮递归扫描扩展种子集合 | 已知 1,815 个方法存在更深依赖 |

## 十、总结

```
整个 JDK 公开 API（74,451 方法）
├── 92.3%（68,749）── 纯字节码，直接翻译，无需手写
└── 7.7%（5,702）─── 需要手写
    ├── 0.5%（388）── ACC_NATIVE 原生方法
    └── 7.1%（5,314）─ 边界方法（调用内部包），按阶段手写

654 个内部类（10,358 方法）
├── 75.1%（7,778）── 有字节码，可继续翻译
│   ├── 58.5% 纯字节码（无依赖）
│   └── 16.6% 有内部依赖（依赖实现后可翻译）
├── 18.9%（1,954）── 必须手写 Rust
│   ├── 1.3%（139）── ACC_NATIVE
│   └── 17.5%（1,815）── 外部内部依赖（已知风险）
└── 6.0%（626）──── 抽象/接口，由子类实现

实现路径
Phase 1（349 类，叶子层）→ 解锁 27.9% 边界方法
Phase 2（+68 类，含 Unsafe）→ 累计 57.2%
Phase 3–6（+79 类）→ 累计 70.4%
循环依赖组（+158 类）→ 累计 100%
```

**最高优先级行动项：**
1. 完成 `jdk/internal/misc/Unsafe`（84 个 native 方法手写 + 325 个方法翻译）
2. 完成 `jdk/internal/util/Preconditions`、`ArraysSupport`、`InternalLock`（全部有字节码，可翻译）
3. 完成 `jdk/internal/reflect/Reflection` 和 `ReflectionFactory`（Class 反射的基础）

以上 6 个类实现完成后，HelloWorld 的 207 个边界方法大部分即可解锁，转译器进入可验证运行的里程碑。

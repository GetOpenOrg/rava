# e2e 查漏补缺与去重的分析方法论

> 定位：2026-10-03 框架依赖包测试地基战役（十轮补缺 133 例 + 剪枝 182 例）的分析逻辑复盘。
> 本文只讲思路与判断标准，过程数据见两份实测报告（`docs/reports/jdk-method-scan.md`、
> `docs/reports/e2e-redundancy-scan.md`），工具见 `scripts/jdk_method_scan.py`、
> `scripts/e2e_redundancy_scan.py`。

---

## 一、问题的形状：一个双向问题

"e2e 测试够不够"不是一个孤立命题，它由两端决定：

```
消费端：框架 / 第三方 jar ——它们运行期真实调用哪些 JDK 类与方法
供给端：tests/e2e 语料    ——每个测试实际行使哪些 JDK 类与方法

覆盖 = 供给端 ∩ 消费端；缺口 = 消费端 − 供给端；冗余 = 供给端内部互相覆盖
```

两端都必须**测量**而不是**声称**。测量基元只有一个：**.class 常量池**。
CONSTANT_Class / Methodref / Fieldref 是符号引用的完备集合——比源码 import 准
（抓 FQCN 内联、隐式 java.lang、静态成员链），比运行观察快（不需要跑起来）。
两个常备脚本就是同一套解析器的两个指向：

- `jdk_method_scan.py`：消费端 → 供给端（找缺口）；
- `e2e_redundancy_scan.py`：供给端内部（找冗余）。

## 二、查漏的漏斗（五层，逐层收窄）

1. **类级扫描**：jar 引用了哪些 JDK 包/类。先排除整块不存在的担忧
   （实测 92 jar 对 sun.misc/jdk.internal 零直接引用——一类问题就地消失）。
2. **方法级**：类覆盖 ≠ 方法覆盖。Methodref 解析后发现类级看不见的洞
   （GCMParameterSpec 零命中、StringTokenizer 11 jar）。
3. **按共用度加权**：方法按"被多少 jar 调用"分层（≥10 jar 核心层 / 5-9 中层 /
   3-4 / 1-2 长尾）。**覆盖义务与使用频度成正比**——长尾不该由 e2e 逐个追，
   那是 pilot 首跑的暴露域；这决定了投入的止损线。
4. **gated 归属**：零命中但属能力判据项的，自动归桶不计缺口
   （K7 JDBC、K9 网络/SSL、C-MT 并发调度、indy 运行模型、跨机默认值、
   K10 资源枚举、安全管理器）。判据："e2e 永远测不了它"或"测了没意义"
   的才进桶——桶是白名单维护的，防滥用。
5. **名字级启发 + 人工裁决**：方法名在语料全文零命中 = 强信号；命中 ≠ 语义已覆盖
   （同名方法可能测的是另一族）。工具只出候选清单，不自动判定——
   否则会把 m5 回归网这类定向测试误判为冗余。

**收敛判据**：每轮补完重跑工具，候选从"族级缺口"（一补一整族）退化为
"族内单点"（descendingMap、RSA、intValueExact 这种角），就是枚举接近完备的
信号——最终 ≥5 jar 可行动缺口收敛到 0，剩余全部有 gated 归属或属长尾。

## 三、起点的冷启动：没有实测数据时怎么办

方法级实测是第五轮才引入的。前四轮靠**多视角人工枚举**冷启动：

1. 按 JDK 类目扫（第一直觉）；
2. 按 pilot 依赖推导（每个框架压什么 JDK 面）；
3. 按框架运行期路径反推（它们初始化/绑定/序列化时真实调什么）；
4. 质疑式逐包核查（假设自己漏了，逐包再过一遍）。

人工枚举的价值：先建立框架知识的映射（TypeSafeMatcher→泛型超类反射、
MDC→ThreadLocal 这类关联），实测数据来了才知道**每个洞护住谁**。
两条独立路径（枚举 × 实测）交叉验证后才敢说"已知缺口清零"。

## 四、去重的镜像逻辑

同样的测量基元，指向内部：

1. 逐测试 javac → 常量池 → 该测试的 JDK 方法集 M(t)；
2. **子集判定只在同目录内做**。反例是设计前提：纯算法族（500 题）的 JDK 面
   全是 Object/StringBuilder/Math，跨目录子集判定会把它们全部误判冗余——
   目录是语义域，同域内"被完全覆盖"才有意义；
3. **置信分层**：面大（≥8）且单一覆盖者全覆 = 高置信；面 4-7 多覆盖者合围 =
   中置信；面 3 保留（证据太弱）；
4. **保护名单**：定向回归网（为已知缺陷写的测试，名字级被覆盖 ≠ 缺陷分支被覆盖）、
   文档点名的金丝雀/规模标杆。教训：文档点名的匹配必须是**精确白名单**——
   子串匹配会让 Logic/Life/ABC 这类英文单词全部假命中；
5. **贪心 + 面守恒**：互为覆盖者的对（StringSwitch ↔ StringSwitchCollision）
   不能一起删。逐个贪心删除、每个删除前断言目录方法面不收缩，删完再全库复验
   （2553 对前后等价）——这是安全网，不是形式。

## 五、确定性约束（每条测试的入场券）

单文件自含、public 类名=文件名、输出逐字确定：固定种子、不打印时间/identityHash/
临时路径/端口号、文件用例临时目录自建自清、网络只用回环、跨机差异面
（os.name、getCanonicalPath 前缀、默认 locale）用布尔断言替代值打印。
期望一律由钉住的 JDK（21）实跑生成，不手写。

## 六、固化下来的工程原则

1. **e2e 与 pilot 分层**：e2e 管 JDK 语义层的回归网，pilot 管 jar 集成层；
   框架测试红了先看地基绿不绿——归因半径决定排查成本。
2. **边界也要覆盖**：能力真覆盖不了的（ServiceLoader 多 provider、资源枚举），
   把可测的边界（空态/异常形态/命中未命中）测掉，其余明确归 K 项。
3. **写测试的副产物是语义发现**：UNDERFLOW.throwException 抛 BufferUnderflowException、
   文本节点 getAttributes() 返回 null、未命名模块 getName() 为 null——撞出来的
   真实语义直接固化为期望，翻译侧将来必须逐字复现。
4. **工具即流程**：拉新 jar 重跑 `jdk_method_scan.py`（默认出缺口）、语料变动
   重跑 `e2e_redundancy_scan.py`（缓存编译，二次跑秒级）。分析能力沉淀为
   常备脚本而不是一次性结论。
